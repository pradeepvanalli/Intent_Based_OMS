## Test infrastructure
* `PostgresTestBase` starts a Testcontainers Postgres (reuse enabled, Ryuk disabled via `~/.testcontainers.properties`).
  Escape hatch when Docker is saturated: `OMS_TEST_JDBC_URL=jdbc:postgresql://localhost:5440/<module>_test OMS_TEST_JDBC_USER=oms OMS_TEST_JDBC_PASSWORD=oms`
  (create the DB in `oms-postgres-1` first). Set `spring.flyway.ignore-migration-patterns=*:missing,*:future` in a module test base when sharing a DB.
* Integration tests are named `*IntegrationTest` / `*Test` (surefire ignores `*IT`).
* `TenantConfigStore.set(key, String)` treats a String as raw JSON: write strings as `Json.write(str)`.

* T1 decisions in the CONFIRM band with no L2 verdict apply the definition `default` deterministically (action `confirm`, layer DEFAULT, `details.confirmFallback` keeps the model's recommendation). ## Margin Replay (oms-simulation, `ai.intentoms.simulation.margin`)
* Purpose: a retailer drops a CSV export of real orders and gets, in under a minute, a report of what Intent OMS would have done differently and how much contribution margin it would have recovered. **Nothing from the file is persisted as an order, plan, reservation or task** — only a `simulation_job` of kind `import` (and, when decisions are on, `decision_record` rows with `mode = SIMULATION`, subject type `margin_replay`).
* `MarginReplayService.submit(fileName, bytes, MarginReplayOptions)` parses synchronously (layout problems → 422 `validation_failed`), inserts the job (`from`/`to` = the file's date range, `sampleLimit` = orders, label `Margin Replay · <file> · N orders`) and replays on a virtual thread bound to the submitter's tenant/principal, committing progress every `oms.simulation.commit-every` orders (per-order rows capped at 50 while RUNNING, full at the end). `submitSample(options)` runs the bundled `replay/shopify-orders-sample.csv` (classpath copy of `docs/examples/data/shopify-orders-sample.csv` via the module pom). `await(id, timeout)` for tests. Limits: 10 MB, 5 000 orders, 100 000 rows.
* `MarginReplayOptions(format auto|shopify|generic, assumeStock=true, unknownSkuCogsRatio=0.6, baseline nearest_node|single_dc:<nodeId>, useDecisions=true)`; `fromParams(Map)` for plain form fields.
  * **assumeStock=true** (default): every active node is treated as holding stock of every SKU, so the comparison isolates network geometry, node economics and policy rather than today's inventory snapshot. `false` reads live ATP (`InventoryService.atp(sku)`); orders with no stock anywhere are skipped with that reason.
* Parsers (`CsvReader` RFC 4180: quoted commas, doubled quotes, multi-line fields, BOM, CRLF; `OrderCsvParser`): Shopify "Orders export" (rows sharing `Name` = one order; header columns from the first row that carries them; `Shipping Province Code`/`Shipping Province`/`Shipping Province Name`; `Lineitem requires shipping=false` lines dropped; `Cancelled at` → skipped) and generic (`order_id, placed_at, sku, qty, unit_price, city, state, zip, country, ship_method, note, customer_tier` + optional `name, shipping_paid, address1, email`). Lines without a SKU are kept under `NAME:<slug>` and flagged (`skuMissing`). Lenient dates (`OrderCsvParser.date`). Tier from Shopify `Tags` (vip → gold).
* `UsGeocoder.locate(city, state, zip, country)`: embedded ~150 largest US cities + 51 state centroids (state names accepted); precedence city → ZIP3 (`ZipGeo`) → state; non-US → empty (order skipped as `non-US destination (XX)`).
* `ReplayPlanner.replay(order, geo, options, jobId, fallbackNow)` → `Result(baseline Arm, intentArm Arm, intent, flags)`. Request lines get catalogue attributes (`CatalogItem.lineAttributes()`: cogs, weight_kg, hazmat, digital…); unknown SKUs get `cogs = price × ratio`, 0.5 kg. Ship method mapping `shipMethod()`: ground | two_day | next_day | same_day | pickup. Candidates are built in the module (capabilities via `DefaultCandidateGenerator.requiredCapabilities`, `canShip`, cutoff via `Transit.cutoffDelayDays(node, placedAt)`, distance from the geocoded point); each order's own `placedAt` is "now".
  * **Baseline** = conventional OMS: ship-as-available from the nearest capable node by great-circle distance (or everything from the single DC, overflow to nearest), no margin floor, no split penalty in the choice, no intent; costed with `EconomicsCalculator.packageEconomics/pnl`, on-time = `RateCard.onTimeProbability(transit, node.reliability())`.
  * **Intent OMS** = `PlanBuilder.build(BuildContext)` with the tenant's `SourcingSettings` (weights, max split, split penalty, margin floor, pickup radius, `NodeRegistry::penalty`), neutral soft scores (no `sourcing_node_score` call, NFR-05 behaviour), policy resolved like `DefaultSourcingService.resolvePolicy` (pickup → pickup_consolidated; intent policy; else `sourcing.channel_default_policy[web]`; `splitOk == false` on a splitting policy → ship_complete; fallback order), below-floor plans flagged (`meetsFloor=false`) rather than blocked.
  * **Intent**: with `useDecisions` and a note, `DecisionService.decide("fulfilment_intent", input, DecisionOptions(subjectType margin_replay, Mode.SIMULATION, version null))` — never escalates, never caches; a value in ACT or CONFIRM band that is a known policy is applied (documented assumption: live T1 CONFIRM applies the channel default); `split_ok`/`is_gift` Nouls read with 0.5 = unknown; any failure or `useDecisions=false` → `IntentDetector.fromKeywords` (together/urgent/separate/pickup/gift regexes).
* Report (`MarginReplayReport`, `ReplayFindings`): `job.results = {kind:"import", options, file{name, bytes, format, rows, orders, warnings}, summary{orders, parsed, planned, skipped, skippedReasons, ordersChanged, nodesShifted, storeToDc, revenue, units, baselineShippingCost, intentShippingCost, shippingSaved, baselineFulfilmentCost, intentFulfilmentCost, fulfilmentSaved, baselineMarginUsd, intentMarginUsd, marginRecoveredUsd, marginRecoveredPerOrder, baselineMarginRatio, intentMarginRatio, baselineSplits, intentSplits, splitsAvoided, splitsAdded, ordersBelowFloorFlagged, baselineOrdersBelowFloor, belowFloorMarginUsd, intentsDetected{gift,urgent,together,pickup,separate}, intentsByBand, ordersWithIntent, ordersWithNotes, avgOnTimeBefore, avgOnTimeAfter, unknownSkuLines, ordersWithUnknownSku, poBoxOrders, hazmatOrders, pickupOrders, dateFrom, dateTo, annualisationDays, estimatedAnnualisedSavings (= marginRecovered × 365 / days, labelled estimate), estimatedAnnualisedOrders, estimateLabel}, topFindings[≤5 deterministic sentences], byRegion[{state, region, orders, changed, baselineCost, intentCost, baselineShipping, intentShipping, shippingSaved, saved, …}], assumptions[], perOrder[OrderSimulation.sampleRow shape + shippingBefore/After, marginBeforeUsd/AfterUsd/DeltaUsd, policy, intent, intentPolicy, intentSource, intentBand, intentRecordId, isGift, urgent, splitOk, belowFloor, poBox, hazmat, unknownSkus, changed, reason, baselineReason, note | {orderId, skipped:true, error}], perOrderTruncated, markdownSummary, processed, partial, durationMs}` plus the flat batch fields (`orders, costPerOrder, baselineCostPerOrder, splitRate, …`) so the generic Simulation page renders import jobs too. "Fulfilment cost" = shipping + labour + packaging + handling + landed + markdown risk + the tenant split penalty, identically in both arms; "shipping" = carrier quotes only.
* REST (`SimulationController`): `POST /api/v1/simulations/import` (multipart `file` + `options` JSON string or form fields; `simulation.run`) → 202 `SimulationJob`; `POST /api/v1/simulations/import/sample` (body = options, optional) → 202. Poll `GET /api/v1/simulations/{id}`. `SimulationConfig` registers a `MultipartConfigElement` (10 MB file / 12 MB request) when the app defines none — Spring Boot's default is 1 MB.
* Samples: `scripts/gen-sample-orders.py` (deterministic, stdlib only) writes `docs/examples/data/shopify-orders-sample.csv` (300 orders / 466 line rows over Sept 2025, demo SKUs + ~15 % unknown, coastal cities, ~10 % notes, 5 PO boxes, 2 non-US, 1 cancelled, 2 lines without SKU, 1 digital line) and `generic-orders-sample.csv` (50 rows).

## Agentic Control Tower (oms-orchestration, `ai.intentoms.orchestration.autonomy`)
* Decides, guardrails and acts: a new decision `stuck_order_diagnosis` (Choice, T2, `config/tenants/demo/decisions/stuck_order_diagnosis.yaml`, golden set `stuck_order_diagnosis_gold.json`, 15 cases) picks the single most likely root cause of a stalled order — `payment_retry_needed | inventory_reallocation_needed | address_confirmation_needed | carrier_lost_in_transit | node_capacity_backlog | awaiting_customer_response | unclear` — from every overlapping signal together (payment, inventory, address, carrier, node, holds, open tasks, customer notes). Three L0 rules cover the clear-cut cases (declined payment with retries remaining, an unverified address, a clean inventory short with no competing node/carrier/payment signal); everything else goes to Jev (heuristic fallback in tests/no key).
* `StuckOrderDiagnosisInputBuilder.build(Order)` assembles the input from real services only — `PaymentService.forOrder`, `InventoryService.atp`, `NodeRegistry.find`, `ShipmentService.forOrder` (carrier "last scan age" proxies the time since the shipment's status last changed — the mock carrier reports a status, not an independent scan timestamp, documented in the Javadoc), `HoldService.active`, `HumanTaskService.list`, `Order.notes()` — and omits a key entirely when the signal is not available (no fake defaults).
* `AnomalyScanner` (`@Scheduled`, `oms.orchestration.autonomy.scan-ms` default 120000; guarded by `oms.orchestration.autonomy.scheduler-enabled` default true, set `false` in `OrchestrationTestBase` so it never fires mid-test-suite) finds candidates per tenant from four signal sources: `orders.placed_at` older than `autonomy.stuck_after_minutes` and still open (anomaly type `no_progress`); `order_risk.score >= autonomy.risk_score_threshold` (read directly — a documented, read-only cross-module query against oms-monitoring's table shape, since no bulk "orders above a score" Java API exists; `sla_breach_risk`); an open `margin_floor_approvals` task older than `autonomy.margin_approval_stale_minutes` (`margin_floor_pending`); an active exception past its `slaDueAt` (`exception_overdue`). Candidates are de-duplicated by order id (60 min window, `AnomalyRepository.existsRecent`) and across the four sources (first match wins). `scanTenant()` is also what `POST /scan-now` and tests call directly; `scanOnce()` fans out over every tenant with open orders.
* Each candidate is diagnosed through the normal `DecisionService.decide("stuck_order_diagnosis", input, DecisionOptions.live("order", orderId, Actor.system("autonomy-scanner")))` — never bypassed, so every autonomous action is traceable from a real `decision_record` like any other decision. `AutonomousActionExecutor.resolve(order, anomalyType, result)`:
  - `result.requiresHuman()` (ESCALATE, or T2 CONFIRM with no L2 verdict): the decision runtime's own `HumanTaskEscalationHandler` already opened the task (queue `decision_escalations`, T2 never routes to `risk_review`); this only looks up the task id via `DecisionEscalationRepository.find(result.escalationId())` to surface it on the feed.
  - `result.acts()`: maps the value to an `AutonomousActionType` (`payment_retry_needed→retry_payment`, `inventory_reallocation_needed→re_source`, `address_confirmation_needed|awaiting_customer_response→notify_customer`, `carrier_lost_in_transit|node_capacity_backlog→re_promise`), estimates a USD impact (merchandise total for re_source/re_promise/retry_payment, 0 for notify_customer/release_hold) and calls `GuardrailService.evaluate`. Allowed → builds a **transient, never-persisted** `ExceptionRecord` + `PlaybookContext` (actor `Actor.decision(recordId)`) and calls the **existing, unmodified** orchestration actions directly as Java objects — `ResourceAction`, `RepromiseAction`, `ReauthorizeAction`, `ContactCustomerAction` — through their normal service calls (`SourcingService.resource`, `CustomerNotifier.notify`, etc.), never a stub. `done` → audit row `outcome=executed`; `skipped`/`failed` (e.g. `ReauthorizeAction` only touches *open* authorisations, so a genuinely declined payment has nothing to reauthorise) → audit row `outcome=failed` and an honest escalation naming what was attempted, rather than pretending the order is handled. Blocked by a guardrail → no audit row, a human task naming exactly which guardrail blocked it (`blockedReason` in the payload).
  - `release_hold`/`refund`/`cancel` are modelled in `AutonomousActionType` (refund/cancel in `NEVER_AUTONOMOUS`, checked in `GuardrailService` regardless of config) but `stuck_order_diagnosis` never produces `release_hold` — its undo is implemented and unit-tested (`AutonomyUndoTest`) but not reachable from the live scanner; a documented gap, not a silent one.
* Guardrails (`AutonomyConfigKeys`, tenant `tenant_config`): `autonomy.enabled` (default **false**), `autonomy.kill_switch` (default false, independent emergency stop), `autonomy.max_actions_per_day` (10), `autonomy.max_usd_impact_per_action` (100.00), `autonomy.allowed_actions` (`[re_source, re_promise, retry_payment, release_hold, notify_customer]`; refund/cancel can never be added), `autonomy.min_confidence_override` (unset; raises, never lowers, the decision's own ACT threshold), plus scanner tuning `autonomy.stuck_after_minutes` (180), `autonomy.risk_score_threshold` (3), `autonomy.margin_approval_stale_minutes` (120), `autonomy.scan_batch` (200). `GuardrailService.evaluate` checks them in the order a person would: kill switch → master switch → hard rule → allow-list → confidence floor → daily cap → dollar cap.
* `AutonomousAction` (table `autonomous_action`, migration V1301) is the audit trail: id, orderId, anomalyType, decisionRecordId, diagnosisValue, confidence, actionTaken, `guardrailSnapshot` (the config in force, including the estimated impact actually used), outcome (`executed|failed`), undoable, `detail` + structured `details` (the action's own result data, e.g. `RepromiseAction`'s before/after promise dates — needed for a precise undo), executedAt, undoneAt/undoneBy/undoReason. `Anomaly` (table `autonomy_anomaly`) is the live-feed row: candidate signal, diagnosis, and how it resolved (`executed` with an `actionId`, or `escalated` with a task id/queue/reason). Ledger events `autonomy.action_executed|action_failed|action_undone` on aggregate `order`.
* `AutonomyUndoService.undo(actionId, reason, actor)`: `re_source` re-sources away from the node the autonomous action moved to (best-effort "if still feasible", not a guaranteed return to the exact prior node); `re_promise` restores the promise dates recorded in `details.groups` before the action ran; `release_hold` re-places the hold from `details.holdType/scopeType/scopeId/reasonCode`. All three refuse with `ConflictException` (409) naming the reason — most commonly "the order has already shipped" — rather than pretending to undo. `retry_payment`/`notify_customer` refuse with `ValidationException` ("not meaningfully reversible") before even trying.
* REST `/api/v1/autonomy` (`AutonomyController`; `exception.read` to view, `exception.work` to undo, `config.admin` for guardrail changes/kill-switch/scan-now): `GET /anomalies`, `GET /actions?from&to&actionType&outcome`, `POST /actions/{id}/undo {reason}`, `GET /guardrails`, `PUT /guardrails {enabled?, maxActionsPerDay?, maxUsdImpactPerAction?, allowedActions?, minConfidenceOverride?}`, `POST /kill-switch {enabled}`, `GET /stats` → `{actionsToday, maxActionsPerDay, usdImpactResolvedToday, maxUsdImpactPerAction, humanEscalations, automationRate}` (automation rate = actionsToday / (actionsToday + humanEscalations) for this capability only), `POST /scan-now` → `{anomaliesFound, anomalies[]}` (runs `scanTenant()` immediately, for live demos).
* Demo data: `config/tenants/demo/tenant-config.yaml` turns `autonomy.enabled` on (max 25/day, $150/action, the default allow-list) for the demo tenant only (ships off everywhere else). Four sample orders were added **to `DemoOrders.all()` in Java** (`AG01`-`AG04`), not to a new `sample-orders.yaml` — the demo tenant's ~25 orders are still the Java `DemoOrders` fallback (no `sample-orders.yaml` file exists for it), and creating one would have *replaced* that whole fallback rather than extending it (`SampleOrdersFile`'s own contract: the file, once present, is used instead of the Java set). Adding to `DemoOrders.all()` is strictly additive and keeps every existing demo script and `DemoSeederIntegrationTest` assertion intact. See `docs/UC_AGENTIC_CONTROL_TOWER.md` for what each order demonstrates.
* Tests: `GuardrailServiceTest` (cap, allow-list, kill switch, confidence override, the refund/cancel hard rule), `AutonomyIntegrationTest` (a scan that executes `notify_customer` end to end when guardrails allow vs. escalates naming the blocked guardrail when they don't on the same order; a declined-payment order diagnosed by the L0 rule that honestly escalates after `ReauthorizeAction` finds nothing open; a low-confidence order that escalates through the decision runtime's own path, not a guardrail block), `AutonomyUndoTest` (a real `re_source` undo, undo-of-an-undone-action rejected, undo after shipping rejected, retry_payment/notify_customer rejected outright).

## Self-Optimizing Order Orchestration (`oms-learning`, `ai.intentoms.learning`)
* New module, dependency root is `platform`/`decision`/`workflow` only; `sourcing`, `inventory`, `copilot`, `simulation`, `orchestration` and `agent` each depend on it (never the reverse) to read learned facts/parameters and drive proposals. See `docs/UC_SELF_OPTIMIZING_ORCHESTRATION.md` for the mechanism and `docs/API.md` for the REST surface.
* `decision_record` (oms-decision, V401) gained `context_features jsonb`, `arms jsonb`, `chosen_arm text`, `propensity double precision default 1.0`, `policy_version int`. `DecisionRuntime.persist()` populates these for every call with `propensity=1.0` (a deterministic choice); only `SourcingPolicyBandit` logs genuine non-1.0 propensity, writing its own `decision_record` row directly via `DecisionRecordRepository` under the synthetic name `sourcing_policy_bandit` (no `decision_definition` exists for it on purpose — it is a bandit arm choice, not a risk-tiered judgement call). `DecisionReplayer.NOT_REPLAYABLE` (oms-simulation) excludes that name from order-level replay for the same reason.
* Nine tables, migration `V1600` (+`V1601` for `node_assignment`/`lane_delivery_sample`/`node_reliability_stat`, FS-02/03): `episode` (one row per decision point, unique on `(tenant_id, decision_id)`), `outcome` (typed payload, FK to episode), `learned_fact` (versioned, `valid_to is null` = active), `segment`, `hypothesis`, `proposal`, `experiment`, `objective_profile`, `learner` (per-tenant governance, PK `(tenant_id, learner_key)`).
* `EpisodeAssembler` (`EventSubscriber` on `decision.evaluated`): opens an episode for every LIVE-mode decision, idempotent on re-delivery. Order id is derived `record.subjectType=="order" ? subjectId : event.correlationId`, so any new decision whose subject/correlation shape differs needs its own mapping here.
* `OutcomeObserver` (`EventSubscriber` on `order.delivered|shipped|out_for_delivery`, `event.delivered|shipped`, `refund.issued|failed`, `payment.failed`, `return.dispositioned`, `oms.returns.disposition|refunded`, `cs.wismo`): maps real ledger events to the typed `OutcomeData` catalog (`DeliveryOutcome`, `FulfillmentOutcome`, `ReturnOutcome`, `PaymentOutcome`, `ContactOutcome`, `InventoryOutcome`), attached to every open/provisional episode for the order. `order.delivered`'s `onTime`/`lateByHours`/`damaged`/`lost` fields are populated by `StandardShipOrderWorkflow.deliver()` comparing each delivered `FulfilmentGroup.promiseDate()` against today — add the same fields at the source for any other workflow that can deliver an order, rather than guessing in the observer. No ledger event carries a chargeback or stranded-inventory signal yet; `PaymentOutcome.chargeback`/`InventoryOutcome` are wired and ready, not fed.
* `RewardCalculator.components(List<OutcomeRecord>)` (pure, unit-testable): only `otd` (on-time), `split`, `fraud`, `cx` terms are computed from outcomes alone; `fill`/`cost`/`inv` default to 0 pending order/finance figures this module deliberately doesn't depend on — extend this function, not the reward formula, when wiring those in. `RewardMaturityService` (`@Scheduled`, `oms.learning.provisional-sweep-ms` default 300000, `oms.learning.maturity-window-days` default 120) moves `OPEN→PROVISIONAL` once any outcome exists, `→MATURE` once `createdAt + maturityWindowDays` has passed, applying the live `ObjectiveProfile` weights (`ObjectiveProfileRepository.live()`, falls back to the `balanced` preset); publishes `episode.matured`.
* `CoverageMonitor` (`@Scheduled`, `oms.learning.coverage-sweep-ms` default 3600000, `oms.learning.coverage-threshold` default 0.8): pauses **every enabled learner for the tenant** (not per-learner-scoped yet) to `L0_OBSERVE` when any decision's outcome coverage over the trailing `oms.learning.coverage-window-days` (default 7) drops below threshold.
* `HumanResolutionCapture` (`EventSubscriber` on `task.completed`, filtered to `type=="decision_escalation"`): independently re-derives the resolution from the task-completed payload (does not depend on `DecisionEscalationTaskSubscriber` having run first — subscriber order isn't guaranteed) and writes it as a `human_resolution` label via the existing `DecisionRecordRepository.label(recordId, label, details)`.
* Fast-loop learners, `.../learning/learner/` (FS/IU/CX/CI/FD/DF): `SourcingPolicyBandit` (epsilon-greedy, 10% exploration floor per arm so a disfavoured policy can never reach exactly 0% selection probability; seeds and persists its random draw in `decision_record.details.randomSeed` so `SourcingPolicyBandit.replay(arms, weights, seed)` reproduces it exactly — NF-04), `NodeReliabilityLearner` (Beta-binomial per node×skuClass×dayPart → `NODE_ON_TIME_RATE`/`NODE_REJECT_RATE`, overlaid live into `SoftScorer` once a node has ≥10 samples), `LaneDeliveryLearner` (→ `LANE_TRANSIT_DAYS_P50`/`P90`/`LANE_ON_TIME_RATE`; **not** wired into `DefaultPromiseService` yet — its latency budget was judged too risky to touch without a dedicated pass), `CiPreferenceLearner` (customer `SPLIT_TOLERANCE` with Bayesian shrinkage `n/(n+5)` toward a segment prior for cold start), `CiSegmentDiscovery` (quantile-bucket segmentation on one feature today, not multi-feature clustering — no ML library in this stack), `FraudThresholdTuner`/`FraudAbuseHypothesisScanner`/`FraudLabelCapture`/`FraudDriftMonitor` (payment_risk/rto_risk/return_risk), `BandThresholdLearner`/`ConfidenceCalibrator`/`GoldenSetGrowthLearner`/`OverrideToRuleLearner`/`ProviderRoutingLearner`/`RuleUtilizationLearner` (all propose `Proposal`s against `oms-decision` artifacts, never call `DecisionStudioService.publish()`/`edit()`/`createDraft()` directly). `AgentReputationLearner` lives in `oms-agent` (not `oms-learning`, to avoid a dependency cycle back to the agent registry it reads) and only ever writes a `LearnedFact(subjectType=AGENT)` — it never calls `AgentRegistry.update()`, so trust-tier changes stay a manual admin action.
* Slow-loop LLM roles extend `oms-copilot` (`.../copilot/learning/`): `AnalystService` (nightly `@Scheduled`, `oms.learning.analyst-cron` default 02:30; `OutcomeDigestBuilder` groups mature episodes by cohort with a minimum cell size of 30, dropped below that — no single order ever reaches the model) → `HypothesisRepository`; `AuthorService` (reads any `OPEN` hypothesis regardless of origin, drafts a `PolicyChangeset` via `CopilotLlmClient` under `LearningSchemas.HYPOTHESES`/the changeset schema, each `PolicyChange` deterministically parsed through its real `@JsonTypeInfo` sealed type rather than trusted as-is; `referencesLiveState` cross-checks a `ThresholdChange`'s `decision`/`band`/`from` against the live artifact before acceptance — the NF "hallucinated lever" guard; hard-refuses any `AllowListChange` adding `refund`/`cancel`) → `Proposal` (status `DRAFT`); `CriticService` (reviews a changeset + its evaluation report → `Review` via `ProposalRepository.setCriticReview`, evidence only, never auto-rejects). Manual triggers: `LearningLlmController` at `/api/v1/learning/llm` (`learning.admin`): `POST /analyst/run`, `POST /author/{hypothesisId}`, `POST /critic/{proposalId}`. Prompt templates `config/copilot/system-{analyst,author,critic}.md`.
* Off-policy evaluator extends `oms-simulation` (`.../simulation/learning/`): `OffPolicyEvaluator` (pure, unit-tested) computes inverse-propensity and doubly-robust lift estimates with a per-arm mean-reward baseline model and a 95% CI from sample variance; propensity clipped at a 0.05 floor so a near-zero-propensity record can't blow up the estimate. `ProposedArmSimulator` replays what a proposal would have chosen for a logged record — fully implemented for `ThresholdChange` only; other `PolicyChange` variants default to "no observed difference," a stated limitation, not a silent one. `ProposalEvaluationService` pulls up to 5000 LIVE `decision_record` rows (90-day lookback) for the target decision, joins each to its episode's reward (skips episodes with no reward, i.e. still `OPEN`), writes the report via `ProposalRepository.markEvaluated` + `LearningEvents.proposalEvaluated`. `EvaluationController`: `POST /api/v1/learning/proposals/{id}/evaluate` (`learning.admin`). Report shape: `{method, sampleSize, baselineReward, proposedRewardEstimate, liftEstimate, confidenceInterval:{lower,upper}, clippedRecords}`.
* Experiment manager, promotion gate and governance (`.../learning/{experiment,promotion,fairness}/`, in `oms-learning` itself): `ExperimentManager` (EX-02/03/04/06 — one running experiment per `target_ref` enforced via `ExperimentRepository.activeFor`; `CANARY` with no `endAt` models the persistent holdout; sticky-per-customer routing via a deterministic hash; the canary early-stop is a z-score heuristic, not full sequential testing, stated as such). `PromotionGuard` (pure, unit-tested): T0 auto-promotes on positive lift + a critic review that isn't `RISKY`; T1 auto-promotes only at the target learner's `autonomyLevel == L3_AUTONOMOUS`; T2 always `NEEDS_APPROVAL`; T3 never autonomous; a postal/zip-scoped change always needs approval regardless of tier (GV-07); kill switch and `maxStep`/weekly change-budget breaches also route to `NEEDS_APPROVAL` rather than silently clipping. `PromotionService` runs as the SYSTEM principal (same pattern as `DecisionEscalationTaskSubscriber`) through `DecisionStudioService`'s real `createDraft→edit→lint→evaluate→publish(emergency=true)` path — emergency publish's 48h retro-review deadline is the safety net on every auto-promotion; only `ThresholdChange` (decision target) and `ParameterChange` (`parameter:` target) are actually auto-applied today, every other `PolicyChange` variant against a decision is refused with a reason rather than falsely marked promoted. `GuardrailBreachMonitor` watches promoted decisions' override rate against the existing 5% KPI and calls `DecisionStudioService.rollback()` + marks the proposal `ROLLED_BACK` on breach. `FairnessReportService` groups by the one behavioral fact available today (split-tolerance terciles, not true segment membership — that needs a table that doesn't exist yet) and flags >10-15 point act-band/override-rate divergence. `CryptoShredPropagation` has real per-customer and tenant-wide learned-fact deletion methods; no deletion *event* exists yet to trigger them automatically (`Tokenizer.shred` is tenant-wide today) — call them directly until one does. `GovernanceController`: `POST /proposals/{id}/promote`, `GET /fairness/{decision}`, `POST /gdpr/purge-customer/{customerId}`. `ExperimentController` (`/api/v1/learning/experiments`): `GET`/`POST`, `POST /{id}/stop`, `POST /holdout`.
* `LearningController` (`/api/v1/learning`, `learning.read`/`learning.admin`): `GET/PUT /learners*`, `POST /kill-switch`, `GET /facts*`, `GET/POST /proposals*` (approve 422s if the caller is the proposal's own author), `GET/PUT /objective`. `LearnerRepository.getOrCreate` lazily registers a learner at `L1_RECOMMEND` on first touch — a learner that has never run simply doesn't appear in `GET /learners` yet.
* MCP (`oms-agent`, new tools, both read-only): `LearningStatusTool` (`learning_status` — learners, proposal-queue counts, recently promoted), `ExplainPolicyChangeTool` (`explain_policy_change {proposalId}` — hypothesis, changeset, evaluation report, critic review, status). Neither can approve or promote.
* Ledger events, aggregate `learning/<id>`, each payload carries a `payloadDigest` SHA-256 (GV-04), via `LearningEvents` (use this, never raw `EventStore.append`): `episode.matured`, `fact.learned`, `hypothesis.raised`, `proposal.drafted`, `proposal.evaluated`, `experiment.started`, `proposal.promoted`, `proposal.rolled_back`.
* UI: `/learning` (`ui/src/pages/learning/LearningConsole.tsx` + `ChangeCard.tsx` + `ObjectiveEditor.tsx`), `ui/src/api/learning.ts`. `WhyDrawer.tsx` gained a "Learned context" section reading `decision_record.policyVersion`/`propensity`/`arms`/`chosenArm` and active facts for the subject. Mock routes in `ui/src/api/mock/learning.ts`.
* Tests worth knowing about: `TenantIsolationTest` (one tenant's outcomes never surface in another tenant's facts/episodes — NF-06), `SourcingPolicyBanditDeterminismTest` (same seed ⇒ same arm, every eligible arm stays reachable), `PromotionGuardTest`, `AuthorServiceHallucinatedLeverTest` (a `ThresholdChange` referencing a wrong `from`/nonexistent decision is rejected before it becomes a `Proposal`), `OffPolicyEvaluatorTest` (synthetic logged records, lift sign and CI correctness).
* Known gaps, stated rather than hidden: safety stock, reservation TTL, inbound-reliability and backorder-action learners (IU-01/02/05/06), the backlog-to-breach learner and decaying store-reject penalty (FS-05/06), fact decay (CI-04), a weekly `TransferRecommendation` report (IU-04), and a general (non-fraud) distribution-shift monitor are not built. `DF-06` (versioned prompt artifacts) is a documented extension point only.
