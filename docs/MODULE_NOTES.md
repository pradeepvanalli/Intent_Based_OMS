## Test infrastructure
* `PostgresTestBase` starts a Testcontainers Postgres (reuse enabled, Ryuk disabled via `~/.testcontainers.properties`).
  Escape hatch when Docker is saturated: `OMS_TEST_JDBC_URL=jdbc:postgresql://localhost:5440/<module>_test OMS_TEST_JDBC_USER=oms OMS_TEST_JDBC_PASSWORD=oms`
  (create the DB in `oms-postgres-1` first). Set `spring.flyway.ignore-migration-patterns=*:missing,*:future` in a module test base when sharing a DB.
* Integration tests are named `*IntegrationTest` / `*Test` (surefire ignores `*IT`).
* `TenantConfigStore.set(key, String)` treats a String as raw JSON: write strings as `Json.write(str)`.

* T1 decisions in the CONFIRM band with no L2 verdict apply the definition `default` deterministically (action `confirm`, layer DEFAULT, `details.confirmFallback` keeps the model's recommendation). ## Margin Replay (oms-simulation, `ai.intentoms.simulation.margin`)
* Purpose: a retailer drops a CSV export of real orders and gets, in under a minute, a report of what Intent OMS would have done differently and how much contribution margin it would have recovered. **Nothing from the file is persisted as an order, plan, reservation or task** — only a `simulation_job` of kind `import` (and, when decisions are on, `decision_record` rows with `mode = SIMULATION`, subject type `margin_replay`).
* `MarginReplayService.submit(fileName, bytes, MarginReplayOptions)` parses synchronously (layout problems → 422 `validation_failed`), inserts the job (`from`/`to` = the file's date range, `sampleLimit` = orders, label `Margin Replay · <file> · N orders`) and replays on a virtual thread bound to the submitter's tenant/principal, committing progress every `oms.simulation.commit-every` orders (per-order rows capped at 50 while RUNNING, full at the end). `submitSample(options)` runs the bundled `replay/shopify-orders-sample.csv` (classpath copy of `docs/examples/data/shopify-orders-sample.csv` via the module pom). `await(id, timeout)` for tests. Limits: 10 MB, 5 000 orders, 100 000 rows.
* `MarginReplayOptions(format auto|shopify|generic, assumeStock=true, unknownSkuCogsRatio=0.6, baseline nearest_node|single_dc:<nodeId>, useDecisions=true)`; `fromParams(Map)` for plain form fields.
  * **assumeStock=true** (default): every active node is treated as holding stock of every SKU, so the comparison isolates network geometry, node economics and policy rather than today's inventory snapshot. `false` reads live ATP (`InventoryService.atp(sku)`); orders with no stock anywhere are skipped with that reason.
* Parsers (`CsvReader` RFC 4180: quoted commas, doubled quotes, multi-line fields, BOM, CRLF; `OrderCsvParser`): Shopify "Orders export" (rows sharing `Name` = one order; header columns from the first row that carries them; `Shipping Province Code`/`Shipping Province`/`Shipping Province Name`; `Lineitem requires shipping=false` lines dropped; `Cancelled at` → skipped) and generic (`order_id, placed_at, sku, qty, unit_price, city, state, zip, country, ship_method, note, customer_tier` + optional `name, shipping_paid, address1, email`). Lines without a SKU are kept under `NAME:<slug>` and flagged (`skuMissing`). Lenient dates (`OrderCsvParser.date`). Tier from Shopify `Tags` (vip → gold).
* `UsGeocoder.locate(city, state, zip, country)`: embedded ~150 largest US cities + 51 state centroids (state names accepted); precedence city → ZIP3 (`ZipGeo`) → state; non-US → empty (order skipped as `non-US destination (XX)`).
* `ReplayPlanner.replay(order, geo, options, jobId, fallbackNow)` → `Result(baseline Arm, intentArm Arm, intent, flags)`. Request lines get catalogue attributes (`CatalogItem.lineAttributes()`: cogs, weight_kg, hazmat, digital…); unknown SKUs get `cogs = price × ratio`, 0.5 kg. Ship method mapping `shipMethod()`: ground | two_day | next_day | same_day | pickup. Candidates are built in the module (capabilities via `DefaultCandidateGenerator.requiredCapabilities`, `canShip`, cutoff via `Transit.cutoffDelayDays(node, placedAt)`, distance from the geocoded point); each order's own `placedAt` is "now".
  * **Baseline** = conventional OMS: ship-as-available from the nearest capable node by great-circle distance (or everything from the single DC, overflow to nearest), no margin floor, no split penalty in the choice, no intent; costed with `EconomicsCalculator.packageEconomics/pnl`, on-time = `RateCard.onTimeProbability(transit, node.reliability())`.
  * **Intent OMS** = `PlanBuilder.build(BuildContext)` with the tenant's `SourcingSettings` (weights, max split, split penalty, margin floor, pickup radius, `NodeRegistry::penalty`), neutral soft scores (no `sourcing_node_score` call, NFR-05 behaviour), policy resolved like `DefaultSourcingService.resolvePolicy` (pickup → pickup_consolidated; intent policy; else `sourcing.channel_default_policy[web]`; `splitOk == false` on a splitting policy → ship_complete; fallback order), below-floor plans flagged (`meetsFloor=false`) rather than blocked.
  * **Intent**: with `useDecisions` and a note, `DecisionService.decide("fulfilment_intent", input, DecisionOptions(subjectType margin_replay, Mode.SIMULATION, version null))` — never escalates, never caches; a value in ACT or CONFIRM band that is a known policy is applied (documented assumption: live T1 CONFIRM applies the channel default); `split_ok`/`is_gift` Nouls read with 0.5 = unknown; any failure or `useDecisions=false` → `IntentDetector.fromKeywords` (together/urgent/separate/pickup/gift regexes).
* Report (`MarginReplayReport`, `ReplayFindings`): `job.results = {kind:"import", options, file{name, bytes, format, rows, orders, warnings}, summary{orders, parsed, planned, skipped, skippedReasons, ordersChanged, nodesShifted, storeToDc, revenue, units, baselineShippingCost, intentShippingCost, shippingSaved, baselineFulfilmentCost, intentFulfilmentCost, fulfilmentSaved, baselineMarginUsd, intentMarginUsd, marginRecoveredUsd, marginRecoveredPerOrder, baselineMarginRatio, intentMarginRatio, baselineSplits, intentSplits, splitsAvoided, splitsAdded, ordersBelowFloorFlagged, baselineOrdersBelowFloor, belowFloorMarginUsd, intentsDetected{gift,urgent,together,pickup,separate}, intentsByBand, ordersWithIntent, ordersWithNotes, avgOnTimeBefore, avgOnTimeAfter, unknownSkuLines, ordersWithUnknownSku, poBoxOrders, hazmatOrders, pickupOrders, dateFrom, dateTo, annualisationDays, estimatedAnnualisedSavings (= marginRecovered × 365 / days, labelled estimate), estimatedAnnualisedOrders, estimateLabel}, topFindings[≤5 deterministic sentences], byRegion[{state, region, orders, changed, baselineCost, intentCost, baselineShipping, intentShipping, shippingSaved, saved, …}], assumptions[], perOrder[OrderSimulation.sampleRow shape + shippingBefore/After, marginBeforeUsd/AfterUsd/DeltaUsd, policy, intent, intentPolicy, intentSource, intentBand, intentRecordId, isGift, urgent, splitOk, belowFloor, poBox, hazmat, unknownSkus, changed, reason, baselineReason, note | {orderId, skipped:true, error}], perOrderTruncated, markdownSummary, processed, partial, durationMs}` plus the flat batch fields (`orders, costPerOrder, baselineCostPerOrder, splitRate, …`) so the generic Simulation page renders import jobs too. * REST (`SimulationController`): `POST /api/v1/simulations/import` (multipart `file` + `options` JSON string or form fields; `simulation.run`) → 202 `SimulationJob`; `POST /api/v1/simulations/import/sample` (body = options, optional) → 202. ## Agentic Control Tower (oms-orchestration, `ai.intentoms.orchestration.autonomy`)
* Decides, guardrails and acts: a new decision `stuck_order_diagnosis` (Choice, T2, `config/tenants/demo/decisions/stuck_order_diagnosis.yaml`, golden set `stuck_order_diagnosis_gold.json`, 15 cases) picks the single most likely root cause of a stalled order — `payment_retry_needed | inventory_reallocation_needed | address_confirmation_needed | carrier_lost_in_transit | node_capacity_backlog | awaiting_customer_response | unclear` — from every overlapping signal together (payment, inventory, address, carrier, node, holds, open tasks, customer notes). Three L0 rules cover the clear-cut cases (declined payment with retries remaining, an unverified address, a clean inventory short with no competing node/carrier/payment signal); everything else goes to Jev (heuristic fallback in tests/no key).
* `StuckOrderDiagnosisInputBuilder.build(Order)` assembles the input from real services only — `PaymentService.forOrder`, `InventoryService.atp`, `NodeRegistry.find`, `ShipmentService.forOrder` (carrier "last scan age" proxies the time since the shipment's status last changed — the mock carrier reports a status, not an independent scan timestamp, documented in the Javadoc), `HoldService.active`, `HumanTaskService.list`, `Order.notes()` — and omits a key entirely when the signal is not available (no fake defaults).
* `AnomalyScanner` (`@Scheduled`, `oms.orchestration.autonomy.scan-ms` default 120000; guarded by `oms.orchestration.autonomy.scheduler-enabled` default true, set `false` in `OrchestrationTestBase` so it never fires mid-test-suite) finds candidates per tenant from four signal sources: `orders.placed_at` older than `autonomy.stuck_after_minutes` and still open (anomaly type `no_progress`); `order_risk.score >= autonomy.risk_score_threshold` (read directly — a documented, read-only cross-module query against oms-monitoring's table shape, since no bulk "orders above a score" Java API exists; `sla_breach_risk`); an open `margin_floor_approvals` task older than `autonomy.margin_approval_stale_minutes` (`margin_floor_pending`); an active exception past its `slaDueAt` (`exception_overdue`). Candidates are de-duplicated by order id (60 min window, `AnomalyRepository.existsRecent`) and across the four sources (first match wins). `scanTenant()` is also what `POST /scan-now` and tests call directly; `scanOnce()` fans out over every tenant with open orders.
* Each candidate is diagnosed through the normal `DecisionService.decide("stuck_order_diagnosis", input, DecisionOptions.live("order", orderId, Actor.system("autonomy-scanner")))` — never bypassed, so every autonomous action is traceable from a real `decision_record` like any other decision. `AutonomousActionExecutor.resolve(order, anomalyType, result)`:
  - `result.requiresHuman()` (ESCALATE, or T2 CONFIRM with no L2 verdict): the decision runtime's own `HumanTaskEscalationHandler` already opened the task (queue `decision_escalations`, T2 never routes to `risk_review`); this only looks up the task id via `DecisionEscalationRepository.find(result.escalationId())` to surface it on the feed.
  - `result.acts()`: maps the value to an `AutonomousActionType` (`payment_retry_needed→retry_payment`, `inventory_reallocation_needed→re_source`, `address_confirmation_needed|awaiting_customer_response→notify_customer`, `carrier_lost_in_transit|node_capacity_backlog→re_promise`), estimates a USD impact (merchandise total for re_source/re_promise/retry_payment, 0 for notify_customer/release_hold) and calls `GuardrailService.evaluate`. Allowed → builds a **transient, never-persisted** `ExceptionRecord` + `PlaybookContext` (actor `Actor.decision(recordId)`) and calls the **existing, unmodified** orchestration actions directly as Java objects — `ResourceAction`, `RepromiseAction`, `ReauthorizeAction`, `ContactCustomerAction` — through their normal service calls (`SourcingService.resource`, `CustomerNotifier.notify`, etc.), never a stub. `done` → audit row `outcome=executed`; `skipped`/`failed` (e.g. `ReauthorizeAction` only touches *open* authorisations, so a genuinely declined payment has nothing to reauthorise) → audit row `outcome=failed` and an honest escalation naming what was attempted, rather than pretending the order is handled. Blocked by a guardrail → no audit row, a human task naming exactly which guardrail blocked it (`blockedReason` in the payload).
  - `release_hold`/`refund`/`cancel` are modelled in `AutonomousActionType` (refund/cancel in `NEVER_AUTONOMOUS`, checked in `GuardrailService` regardless of config) but `stuck_order_diagnosis` never produces `release_hold` — its undo is implemented and unit-tested (`AutonomyUndoTest`) but not reachable from the live scanner; a documented gap, not a silent one.
* Guardrails (`AutonomyConfigKeys`, tenant `tenant_config`): `autonomy.enabled` (default **false**), `autonomy.kill_switch` (default false, independent emergency stop), `autonomy.max_actions_per_day` (10), `autonomy.max_usd_impact_per_action` (100.00), `autonomy.allowed_actions` (`[re_source, re_promise, retry_payment, release_hold, notify_customer]`; refund/cancel can never be added), `autonomy.min_confidence_override` (unset; raises, never lowers, the decision's own ACT threshold), plus scanner tuning `autonomy.stuck_after_minutes` (180), `autonomy.risk_score_threshold` (3), `autonomy.margin_approval_stale_minutes` (120), `autonomy.scan_batch` (200). `GuardrailService.evaluate` checks them in the order a person would: kill switch → master switch → hard rule → allow-list → confidence floor → daily cap → dollar cap.
* `AutonomousAction` (table `autonomous_action`, migration V1301) is the audit trail: id, orderId, anomalyType, decisionRecordId, diagnosisValue, confidence, actionTaken, `guardrailSnapshot` (the config in force, including the estimated impact actually used), outcome (`executed|failed`), undoable, `detail` + structured `details` (the action's own result data, e.g. `RepromiseAction`'s before/after promise dates — needed for a precise undo), executedAt, undoneAt/undoneBy/undoReason. `Anomaly` (table `autonomy_anomaly`) is the live-feed row: candidate signal, diagnosis, and how it resolved (`executed` with an `actionId`, or `escalated` with a task id/queue/reason). Ledger events `autonomy.action_executed|action_failed|action_undone` on aggregate `order`.
* `AutonomyUndoService.undo(actionId, reason, actor)`: `re_source` re-sources away from the node the autonomous action moved to (best-effort "if still feasible", not a guaranteed return to the exact prior node); `re_promise` restores the promise dates recorded in `details.groups` before the action ran; `release_hold` re-places the hold from `details.holdType/scopeType/scopeId/reasonCode`. All three refuse with `ConflictException` (409) naming the reason — most commonly "the order has already shipped" — rather than pretending to undo. `retry_payment`/`notify_customer` refuse with `ValidationException` ("not meaningfully reversible") before even trying.
* REST `/api/v1/autonomy` (`AutonomyController`; `exception.read` to view, `exception.work` to undo, `config.admin` for guardrail changes/kill-switch/scan-now): `GET /anomalies`, `GET /actions?from&to&actionType&outcome`, `POST /actions/{id}/undo {reason}`, `GET /guardrails`, `PUT /guardrails {enabled?, maxActionsPerDay?, maxUsdImpactPerAction?, allowedActions?, minConfidenceOverride?}`, `POST /kill-switch {enabled}`, `GET /stats` → `{actionsToday, maxActionsPerDay, usdImpactResolvedToday, maxUsdImpactPerAction, humanEscalations, automationRate}` (automation rate = actionsToday / (actionsToday + humanEscalations) for this capability only), `POST /scan-now` → `{anomaliesFound, anomalies[]}` (runs `scanTenant()` immediately, for live demos).
* Demo data: `config/tenants/demo/tenant-config.yaml` turns `autonomy.enabled` on (max 25/day, $150/action, the default allow-list) for the demo tenant only (ships off everywhere else). Four sample orders were added **to `DemoOrders.all()` in Java** (`AG01`-`AG04`), not to a new `sample-orders.yaml` — the demo tenant's ~25 orders are still the Java `DemoOrders` fallback (no `sample-orders.yaml` file exists for it), and creating one would have *replaced* that whole fallback rather than extending it (`SampleOrdersFile`'s own contract: the file, once present, is used instead of the Java set). Adding to `DemoOrders.all()` is strictly additive and keeps every existing demo script and `DemoSeederIntegrationTest` assertion intact. See `docs/UC_AGENTIC_CONTROL_TOWER.md` for what each order demonstrates.
* Tests: `GuardrailServiceTest` (cap, allow-list, kill switch, confidence override, the refund/cancel hard rule), `AutonomyIntegrationTest` (a scan that executes `notify_customer` end to end when guardrails allow vs. escalates naming the blocked guardrail when they don't on the same order; a declined-payment order diagnosed by the L0 rule that honestly escalates after `ReauthorizeAction` finds nothing open; a low-confidence order that escalates through the decision runtime's own path, not a guardrail block), `AutonomyUndoTest` (a real `re_source` undo, undo-of-an-undone-action rejected, undo after shipping rejected, retry_payment/notify_customer rejected outright).

The runtime logs propensity 1.0; `SourcingPolicyBandit` logs the applied arm with its true epsilon-greedy draw probability and keeps a sampled-but-unused arm in `details.shadow`.
* **Episodes (OC-02).** One per decision point: `decision_point_key = decision|subjectType|subjectId-or-orderId|line|fg` (unique). Re-evaluations update `last_decision_id` / `evaluation_count` (V1603 merged historical duplicates). `injection_screen` is excluded.
* **Outcomes (OC-03/05).** `OutcomeMapper` beans (`CoreOutcomeMapper`, fraud/contact, inventory) map ledger events to `OutcomeData`; `OutcomeObserver` attaches each to the episodes of its order and of its own subject (returns by RMA), scoped to the named fulfilment group/lines when present, at most once per (episode, event). Rule-based attribution (stock/node/carrier/customer) is stored with the reward.
* **Rewards (OC-04, §7).** Seven terms normalised to [0,1] (fill, on-time, cost/order value, splits, fraud loss, contacts, aged-stock relief). Each term matures on its own window (`MaturityWindows`: delivery 14, contact 30, return 45, chargeback 120 days; tenant `learning.maturity.*`); MATURE when every weighted term is mature; an episode with no outcome at all matures with a null reward. Penalty terms (cost, splits, fraud, contacts) are scaled to [0,1] by `RewardBaselineService` (weekly, Mon 06:30 UTC; `POST /learning/jobs/reward-baseline/run`): the 95th percentile of each raw term over the last 90 days of the persistent holdout's episodes when the holdout has at least 30 for that term (the baseline policy, so the yardstick does not drift with what learning changed), else over all recent episodes. `learning.reward_baseline` records the scales, `samples`, `sources` per term and `source` overall (holdout, recent, mixed or none).
* **Coverage (OC-07).** `CoverageMonitor` measures, per decision some learner reads, the share of episodes older than the observation lag (3 days) that have an outcome; below 80% it pauses only the learners reading that decision (judged by their worst decision) and resumes them on recovery.
* **Governance (GV-01..07).** `LearnerGovernance` gate: global `oms.learning.kill-switch` → tenant `learning.enabled` / `learning.kill_switch` → learner switch → pause (separate from autonomy). `PromotionGuard`: L0 never promotes; L1 auto-promotes T0 only after replay and a passed shadow run; L2 T0; L3 T0/T1 within budget; T2 approval; T3 never; refunds, cancellations, pricing, objective and autonomy changes always need a person; adding refund/cancel to an autonomous allow-list is refused. Autonomy changes need `learning.admin` + `config.admin`. Postal-code-scoped approvals need a reason code (`learning.postal_reason_codes`). Every governance transition is a ledger event (aggregate `learning`).
* **Live use.** `ParameterResolver` serves a learned value only after a promoted `parameter:live:<family>` change (range, max step) while its learner is on, unpaused and above L0; otherwise the static value. Families: `sourcing.node_reject_rate`, `sourcing.node_on_time_rate`, `sourcing.reject_penalty`, `sourcing.node_backlog_breach`, `sourcing.policy_bandit`, `sourcing.aged_stock_tiebreak`, `promise.lane_transit_days`, `promise.lane_calibration`, `promise.buffer_days`, `monitoring.warn_early_threshold`, `cs.appeasement_level`, `inventory.safety_stock`, `inventory.reservation_ttl`, `inventory.inbound_reliability`, `customer.preferences`, `fraud.agent_reputation`, `fraud.agent_dispute_rate`, `fraud.address_reuse_count`, `decision.calibration`.
* **Decision fabric hook.** `DecisionLearningHooks` (oms-decision SPI) → `LearningDecisionHooks` delegating to `FeatureContributor`, `ConfidenceCalibration`, `ProviderRouter`, `ExperimentRouter` beans; LIVE/SHADOW only; facts merged before hashing and listed in `details.learnedFacts`; the trace's `learning` section shows them.
* **Learners** (27 on the demo tenant): fulfilment and promise (node reliability, lane transit, bandit + bandit reward, backlog breach, sourcing weights, promise buffer, warn early, appeasement level), fraud (threshold tuner, abuse scanner, drift via monitor, agent reputation), inventory (stock age, safety stock, reservation TTL, transfers, inbound reliability, backorders), customers (preferences, segments via plain-Java k-means), decision quality (band thresholds, calibration, golden-set growth, override-to-rule, provider routing, rule utilisation). Slow loop: Analyst/Author/Critic in oms-copilot (nightly author run, schema and prompt hashes recorded, monthly `learning.llm_budget_usd_per_month`).
* **Evaluation and experiments.** oms-simulation replays decision targets (threshold fast path or full re-simulation, then IPS/doubly-robust with a CI); config and parameter targets get an observational comparison or `no_counterfactual` and need a person. Experiments: shadow (real shadow version), sticky canary with an always-valid sequential test, persistent holdout routed to the pre-learning baseline for promoted decision changes, one running experiment per target and mode. `GuardrailBreachMonitor` rolls back on override rate, p95 latency, contact rate and fraud false-positive rate (ignores `system:demo-seed`).
* **Reference data.** `oms-app/.../glue/soo/SooDemoSeeder` (demo tenant, `oms.demo.soo-seed`, after `DemoSeedCompletedEvent`) seeds ~135 days of labelled history through the real learners and services; `GET /api/v1/learning/seed-status`. `scripts/usecases/uc8-self-optimizing.sh` drives the live flow.
* **Known limits.** AC2/AC3 (holdout lift with CI above zero; no guardrail worse over four weeks) need weeks of real traffic — the mechanism runs on seeded data, labelled as such. Holdout routing does not cover config/live-parameter changes. CX-02 conversion and chargebacks need a real storefront and Stripe account (ingestion endpoints exist).
