1. Summary
Intent OMS is a configurable, event-sourced order management system where every
order decision runs through a layered decision stack — deterministic rules, Jev typed
decisions, LLM reasoning, then human approval — and every decision is versioned,
explainable and replayable.

Product thesis. All five reference vendors shipped AI agents between late 2025 and
August 2026, but each agent assists a human or explains a rules engine. The decision itself
is still buried in configuration that only implementers can change.

Intent OMS makes the decision a first-class, business-owned object. Business users edit
criteria, prompts and thresholds; Jev returns typed, calibrated answers in 70–500 ms; the
LLM handles only open-ended reasoning; hard guardrails protect margin, compliance and
money movement.

4. Vision, principles, goals
Vision: every order decision is a typed, explainable, business-owned function, and every
order can be operated by a person or an agent through the same governed interface.

Design principles

 1. Deterministic first, typed second, generative last. Hard constraints live in rules. Jev
     answers bounded judgments. The LLM handles open-ended reasoning, drafting and
     configuration authoring only.
 2. Decisions are data. A decision definition (state schema, questions, criteria,
    thresholds, fallback) is versioned, tested, approved and replayable like code.




                                                                                                   Page 5 of 41
Intent OMS — Product Requirements




 3. Confidence is a routing signal. Every probabilistic decision maps confidence to act,
     confirm or escalate, with bands set by the risk of the action.
 4. The ledger is the truth. Orders are event-sourced; any order can be rebuilt and any
     decision re-run against the exact inputs it saw.
 5. Agent-native, human-governed. UI, integrations and AI agents call the same APIs
     under the same permission model. No back doors for agents.
 6. Model-agnostic. Jev is the default System One provider; LLMs are pluggable; no
     single-vendor lock-in.
 7. Margin-aware by default. Sourcing, promise, appeasement and return decisions all see
    order contribution margin.
 8. Change without deploys. States, transitions, decisions and prompts change at
     runtime, behind simulation and approval.

Goals (targets to validate with design partners within 6 months of go-live)

     90% or more of orders reach a terminal state with no human touch.
     A T0–T1 policy change goes from idea to production in under one business day.
     Split-shipment rate falls 15% against the customer's baseline without lowering on-time
     delivery.
     No order ships below the profitability floor without a recorded approval.
     A mid-market brand goes live in 12 weeks or less.

Non-goals: WMS and TMS execution, storefront and checkout UI, product information
management, demand planning, building payment or tax engines, and any autonomous
money movement outside declared bounds.

6. Reference architecture
Orders enter through one gateway, live in an event-sourced core, and every judgment a
service needs goes through the decision fabric, which acts only inside the gate that
governance allows.

records and drives state; domain services ask the fabric for decisions; governance sets
what each layer may do. Jev (highlighted) is the default engine for typed decisions.

9. Jev integration design
Jev is the default engine for bounded order decisions because it returns only typed
values with calibrated probabilities, in 70–500 ms, at $0.042 per million input tokens with
output free (TrueFoundry). A 15,000-token sourcing state (100 candidate nodes)
therefore costs about $0.0006 per call at list price.

What Jev is, and its limits (as of 4 October 2026)



                                                                                     Page 26 of 41
Intent OMS — Product Requirements




     Released in early access on 15 September 2026 by TypeSafe AI as its first "System One"
     model; proprietary and hosted only (Wikipedia).
     Three primitives: Choice (pick one of up to 255 options), Score (rate on a rubric) and
     Noul (probability a statement is true). Choice and Score return a 0–1 confidence; Noul
     returns only its probability (TypeSafe docs).
     Input is text or JSON state; no images or audio. Questions in one call run in parallel and
     independently, so adding questions barely changes latency.
     It writes no rationale, so explanations must come from decomposed questions and the
     trace.
     On TypeSafe's own four-workflow benchmark it reaches roughly 68% accuracy —
     good, not superhuman (Eden AI). Every decision must be measured on our own data
     before it acts.

Integration rules

 1. Atomic questions, composed in code. One judgment per question; weights for
     combining them live in configuration (TypeSafe's composite-scoring pattern).
 2. Minimal typed state. The state builder passes the exact fields a question concerns,
     never the whole order document.
 3. Speculative fan-out. Ask every question a decision point might need in one call; code
     decides which answers matter.
 4. Escape option in every Choice (GR-03).
 5. Two-stage for large sets. Over 255 options: Score each candidate, keep the top K, then
     Choose among them.
 6. Reason codes by decomposition. Ask reason-code Nouls alongside the main question
     and store them with the decision.
 7. Gate Nouls on the same scale. Use confidence = |2p − 1| so Nouls and Choices share
     one threshold scale (TypeSafe confidence docs).
 8. Verify calibration first. Run each decision in shadow mode until accuracy at each
     confidence level is known; only then switch on autonomy.
 9. Never single-vendor. The DecisionProvider interface falls back to LLM structured
     output, then to L0 defaults, if Jev is unavailable, rate-limited or repriced.

  Term                              Meaning

  BOPIS / BORIS                     Buy online, pick up in store / buy online, return in

                                    accuracy
